# ziskos-staticlib

Produces `libziskos_staticlib.a` (`libziskos.a`), a static archive that exposes
ZisK's standard C interface (accelerators, IO and lifecycle) for linking into a
host application written in C or Rust.

Unlike a guest program —which *is* the whole `no_std` binary and owns the
`#[global_allocator]`—, here ziskos is linked into an application that already
has its own allocator. To keep them from colliding, this crate:

1. **Isolates ziskos's allocator** at the symbol level (its heap is a private
   static buffer, and its allocator symbols are made `STB_LOCAL`).
2. **Wraps every public function** so the internal heap is rewound before each
   call (see [Architecture](#architecture)).

## Architecture

The real implementations live in the `ziskos` crate. When compiled as a
staticlib (cfg `zisk_staticlib`, enabled by the `staticlib` feature), those
functions **drop their `#[no_mangle]`** so they don't clash with the wrappers;
they remain reachable only through their Rust path.

Each public C symbol (`zkvm_keccak256`, `read_input`, …) is provided by a
**wrapper** generated by the `wrap_export!` macro in [`src/lib.rs`](src/lib.rs),
which:

1. Calls `reset_sys_alloc()` to rewind ziskos's private bump heap.
2. Delegates to the internal implementation.
3. (Optional, `alloc-stats` feature) updates the peak memory usage.

Because the wrappers live in this crate and `ziskos` does not depend on it, **no
internal call between ziskos functions re-enters through a wrapper**: the reset
only happens at the host → library boundary. The library is single-threaded, so
the allocator state (`static mut`) needs no synchronization.

## Building the staticlib

The recommended way is the `libziskos` make target, which compiles with *fat
LTO*, finalizes the bitcode into a single native object, localizes (STB_LOCAL)
the allocator symbols and verifies the isolation invariants:

```bash
make libziskos
```

This is a discoverable, dev-facing wrapper around the isolated build script that
CI also uses ([`.github/scripts/build-libziskos-isolated.sh`](../.github/scripts/build-libziskos-isolated.sh));
you can call the script directly if you prefer. Enable cargo features with
`FEATURES`, e.g. `make libziskos FEATURES=alloc-stats`.

> **Note:** a plain `cargo build -p ziskos-staticlib` does **not** produce a
> usable library. Without `--target riscv64ima-zisk-zkvm-elf` the whole crate is
> gated out (`#[cfg(zisk_guest)]`) and the archive is empty; even with the
> target it skips the allocator-isolation post-processing. Use `make libziskos`.

Output:

```
target/riscv64ima-zisk-zkvm-elf/release/libziskos_staticlib.a
```

### Script environment variables

| Variable         | Default                     | Purpose                                          |
|------------------|-----------------------------|--------------------------------------------------|
| `ZISK_TARGET`    | `riscv64ima-zisk-zkvm-elf`  | Compilation target.                              |
| `ZISK_TOOLCHAIN` | `zisk`                      | Rust toolchain.                                  |
| `ZISK_FEATURES`  | (empty)                     | Cargo features to enable (e.g. `alloc-stats`).   |

### Direct build (without isolation)

For fast iteration during development (not suitable for linking against the
host, since it does not apply the allocator isolation):

```bash
cargo +zisk build -p ziskos-staticlib --release --target riscv64ima-zisk-zkvm-elf
```

### Requirements

- The `zisk` toolchain installed (includes the `riscv64ima-zisk-zkvm-elf` target).
- The `llvm-tools` component for that toolchain (the script tries to install it).

## Including the library in the host

Link `libziskos_staticlib.a` and use the exported C symbols. The interface
follows the [zkvm-standards](https://github.com/eth-act/zkvm-standards)
specification (accelerators and IO).

Available public symbols (among others):

- **Accelerators**: `zkvm_keccak256`, `zkvm_sha256`, `zkvm_ripemd160`,
  `zkvm_modexp`, `zkvm_bn254_*`, `zkvm_bls12_*`, `zkvm_secp256k1_*`,
  `zkvm_secp256r1_verify`, `zkvm_blake2f`, `zkvm_kzg_point_eval`.
- **IO**: `read_input`, `write_output`.
- **Lifecycle**: `zkvm_init`, `zkvm_deinit`.

### Linking from C

```c
// zkvm_accelerators.h / zkvm_io.h define the signatures and types.
zkvm_init();
// ... calls to zkvm_keccak256, read_input, write_output, ...
zkvm_deinit();
```

```bash
cc main.c -L target/riscv64ima-zisk-zkvm-elf/release -lziskos_staticlib -o app
```

### Linking from Rust

```rust
extern "C" {
    fn zkvm_init();
    fn zkvm_deinit();
    fn zkvm_keccak256(data: *const u8, len: usize, output: *mut /* zkvm_keccak256_hash */ u8) -> i32;
}
```

And point the linker at the directory and the lib (a `build.rs` with
`cargo:rustc-link-lib=static=ziskos_staticlib` and `cargo:rustc-link-search=...`).

## C++ support

`_start` runs C++ static constructors before `main` and static destructors after
`main` returns, as required by the zkvm-standards. This works for any host
language whose static initializers land in `.init_array` (C++, and Rust
ctor-style crates).

- **Constructors:** `_start` walks `.init_array` (bracketed by the linker symbols
  `__init_array_start` / `__init_array_end`) before calling `main`.
- **Destructors:** static-object destructors are registered at construction time
  via `__cxa_atexit(dtor, obj, &__dso_handle)` and run after `main` returns via
  `__cxa_finalize`, followed by `.fini_array` (in reverse order).
- **Freestanding runtime:** the library provides **weak** `__cxa_atexit`,
  `__cxa_finalize` and `__dso_handle`, so freestanding C++ links without a
  `libsupc++`. If the host links its own C++ runtime, those strong symbols take
  precedence. The `__cxa_atexit` table is fixed-capacity (single-threaded guest).
- **Zero cost when unused:** with no static initializers the arrays are empty and
  the loops are no-ops; nothing pulls in the `__cxa_*` symbols.
- **Allocator:** constructors/destructors that allocate use the **host program's**
  allocator (`operator new` / `malloc`), never ziskos's private bump heap (which
  is rewound per call) — see [Architecture](#architecture). The host must provide
  a persistent allocator for its own (and C++) allocations.

### Linker script

Use ZisK's own [`ziskbuild/zisk_linker_script.ld`](../ziskbuild/zisk_linker_script.ld).
It places `.init_array` / `.fini_array` (with `KEEP`) in the read-only ROM
segment and defines `__init_array_start` / `__init_array_end` /
`__fini_array_start` / `__fini_array_end`. The runtime references these bounds as
**strong** symbols, so the linker script must define them. In practice this is
not a burden: stock GNU ld and LLD always provide these symbols automatically
(even without explicit script lines), and when the arrays are empty the
construction loops are no-ops.

If you bring your own script, keep the ZisK memory windows (code and read-only
data in ROM at `0x8000_0000`, writable data in RAM at `0xa000_0000`) — the ELF
interpreter rejects loadable segments outside them.

### Building a C++ host

Match the staticlib's ISA/ABI and use the `medany` code model (the RAM lives at
high addresses):

```bash
riscv64-unknown-elf-g++ -march=rv64ima -mabi=lp64 -mcmodel=medany \
  -ffreestanding -fno-exceptions -fno-rtti -c main.cpp -o main.o
riscv64-unknown-elf-g++ -march=rv64ima -mabi=lp64 -mcmodel=medany \
  -nostdlib -nostartfiles -T ../ziskbuild/zisk_linker_script.ld \
  main.o target/riscv64ima-zisk-zkvm-elf/release/libziskos_staticlib.a -o guest.elf
```

### Limitations

Verified against the program-segment ELF interpreter (see the regression test at
[`elf-regressions/cpp_static_init/`](../elf-regressions/cpp_static_init/)):

- **`thread_local` is not supported.** The linker script declares no `PT_TLS`
  segment, so any TLS symbol is a link error
  (`has an STT_TLS symbol but doesn't have a PT_TLS segment`).
- **`.preinit_array` is not run.** The runtime walks `.init_array` only.
- **Legacy `.ctors` / `.dtors` are ignored.** Toolchains configured with
  `--disable-initfini-array` emit these instead of `.init_array`, and their
  entries are silently never executed. Modern GCC/Clang emit `.init_array`.
- **At most 64 static destructors.** `__cxa_atexit` has a fixed-capacity table;
  the compiler discards its return value, so registrations beyond `MAX_ATEXIT`
  are dropped without a diagnostic.
- **No C++ exception or RTTI runtime is provided.** Build with
  `-fno-exceptions -fno-rtti` unless the host links its own `libsupc++`.

## Adding new functions

To expose an internal ziskos function through the staticlib:

1. **In `ziskos`**, make sure the function is not `#[no_mangle]` in the staticlib
   build. The pattern used is:

   ```rust
   #[cfg_attr(all(not(feature = "hints"), not(zisk_staticlib)), no_mangle)]
   pub unsafe extern "C" fn new_function(/* ... */) -> /* ... */ { /* ... */ }
   ```

   (without `not(zisk_staticlib)` the symbol would clash with the wrapper).

2. **In [`src/lib.rs`](src/lib.rs)**, inside the `exports` module, add a
   `wrap_export!` invocation with the **exact signature** and the **full path**
   of the implementation:

   ```rust
   wrap_export!(fn new_function(arg: *const u8, len: usize) -> zkvm_status
       => ziskos::zisklib::path::new_function);
   ```

   - Signatures use the C types from `zkvm_interface` (already imported above).
     If you need a new type, add it to the `use zkvm_interface::{…}` block.
   - The first identifier (`new_function`) is the **exported symbol**; the path
     on the right is the real implementation.

3. **In the verification script**
   [`build-libziskos-isolated.sh`](../.github/scripts/build-libziskos-isolated.sh),
   add the name to `REQUIRED_GLOBAL` if you want the build to fail when the
   symbol is not exported as global.

The macro automatically generates the wrapper with `reset_sys_alloc()` and, if
the `alloc-stats` feature is enabled, the peak-memory update.

## Internal allocator statistics (`alloc-stats`)

The `alloc-stats` feature measures the **peak bytes** handed out by ziskos's
isolated bump allocator over the lifetime of the program.

### Enabling it

```bash
make libziskos FEATURES=alloc-stats
```

(equivalently `ZISK_FEATURES=alloc-stats .github/scripts/build-libziskos-isolated.sh`).

### What it does

- After each host call, the wrapper invokes `update_max_used_sys_alloc()`, which
  computes the current usage (`HEAP_POS - HEAP_BOTTOM`) and keeps the maximum.
- On shutdown, `zkvm_deinit` prints to the UART (no std):

  ```
  ziskos-isolated-allocator use: <N> bytes
  ```

  where `<N>` is the accumulated maximum.

### Querying the maximum from the host

Besides the automatic dump in `zkvm_deinit`, a function is exported to read the
peak at any time:

```rust
extern "C" {
    fn get_max_used_sys_alloc() -> usize;
}
```

Without the feature, none of this is compiled: zero cost in the default build.

### Adjusting the heap size

The isolated heap is a static buffer in `.bss`. Its size (`HEAP_SIZE`) is defined
in [`ziskos/entrypoint/src/alloc/alloc.rs`](../ziskos/entrypoint/src/alloc/alloc.rs)
(8 MiB by default). Use the stats to size it to your real working set.

The default was chosen empirically: measuring 60 MiB "killer blocks" with the
`alloc-stats` feature, the peak usage of the isolated bump allocator was just
over 1 MiB. 8 MiB leaves a comfortable safety margin over that observed peak
while keeping the reserved `.bss` address space small.
